# MCP authorization (spec revision 2026-07-28) and this repo

Source: https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/authorization and the linked
specification pages (basic/authorization, authorization-server-discovery, client-registration,
security-considerations, security_best_practices). This page records which requirements apply to
the two runtimes here, how each is met, and what would have to change if an HTTP MCP transport is
ever added. Keep it current when touching `src/auth`, `src/integrations/link.ts`, or `src/server`.

## Which parts apply

| Runtime                                                | Transport                     | Spec position                                                                                                                           | Consequence                                                                                                                                                                                                    |
| ------------------------------------------------------ | ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| stdio MCP server (`src/index.ts`, `src/mcp-server.ts`) | stdio                         | "Implementations using an STDIO transport SHOULD NOT follow this specification, and instead retrieve credentials from the environment." | No OAuth resource-server role. Credentials (client id and secret, encryption key, user id and roles) come from the environment; the per-user Workday sign-in is an upstream OAuth flow, not MCP authorization. |
| HTTP integration runtime (`src/server/main.ts`)        | HTTP, but not an MCP endpoint | The runtime serves Slack webhooks and the Workday OAuth redirect; it does not expose MCP over HTTP.                                     | The resource-server requirements (Protected Resource Metadata, `WWW-Authenticate`, audience validation) do not apply today. Callers are authenticated by Slack request signing plus `identity_links`.          |

Both runtimes act as an OAuth client toward Workday. The spec's client-side rules (PKCE, state,
redirect handling, secure storage, no token leakage) are the ones that bite, and they are listed below.

## If an HTTP MCP transport is added later

Do not reuse the Slack runtime's identity path. An MCP-over-HTTP endpoint must become an OAuth 2.1
resource server as the spec describes:

1. Serve Protected Resource Metadata at `/.well-known/oauth-protected-resource/<mcp path>` (root fallback) with `resource`, `authorization_servers`, and a minimal `scopes_supported`.
2. Reply `401` with `WWW-Authenticate: Bearer resource_metadata="...", scope="..."` when a token is missing or invalid, and `403` with `error="insufficient_scope"` plus the full scope set for the operation when scopes are short.
3. Validate the access token's audience is this server (RFC 8707 Section 2) and reject every other token. Never forward the MCP access token to Workday; the Workday token stays the per-user token obtained through the existing link flow.
4. Prefer Client ID Metadata Documents for client registration; Dynamic Client Registration is deprecated in this revision.
5. Keep `Mcp-Session-Id` out of authorization decisions.

The stdio server stays as it is: credentials from the environment, no MCP-level OAuth.
